# Gemma4・システムプロンプト編集の開発版

開発ブランチ：`dev/gemma4-planner`。mainへはまだ統合していません。

## 接続とモデル選択

`workflows/all_in_one_magic_battle_gemma4.json` を読み込みます。「台本用モデル・Qwen／Gemmaをここで選択」の `clip_name` だけを切り替えます。MOSSは「MOSS画像生成用Qwen・このモデルは固定」から受け取るため、画像生成用Qwenまで変更されません。

- Gemma4：`gemma4_e4b_it_int8_convrot.safetensors`
- 既存Qwen：`qwen3.5_9b_int8_convrot.safetensors`

Gemma4は [Comfy-Org/gemma-4](https://huggingface.co/Comfy-Org/gemma-4/tree/main/text_encoders) のComfyUI対応E4B instructモデルを使用します。配布名を変えず `models/text_encoders` へ置きます。Ollamaの `gemma4:e4b` と同じE4B系列ですが、保存形式と量子化が異なるため、同一出力を保証しません。Ollamaへの接続や設定の読取は行いません。

`type` は付属例では `moss_image` のままです。今回のComfyUIは重みからGemma4を自動判別する分岐を持ち、Qwenへ選択を戻した時にも従来のMOSS用エンコーダーとして読み込める条件にそろえています。

既存のQwen共用ワークフロー3種類も残しています。こちらは台本とMOSSが従来どおり同じ読込ノードを参照します。Gemma版ではモデルが1種類増えるため、GemmaからMOSS用Qwenへの読み込み・退避のコストが加わり得ます。両読込ノードを同じQwen・同じ設定にした場合、ComfyUIの入力シグネチャによる出力キャッシュを再利用できる構成ですが、全キャッシュモードでの動作や時間差は保証しません。

## システムプロンプト

「① 作りたい動画をここに1つ入力」の `system_prompt` を編集します。初期値は従来の演出方針です。人物、場面、カメラ、文体などの方針を変えられます。

ノードは編集内容の後ろへ、4カットのJSON構造を指定する固定の指示を付けます。これはMOSSとH3の共通台本を読むために必要な形式です。システムプロンプトを省略した過去のAPIワークフローでは、従来と同じ全文を使用します。

同じ設定で比較する場合は、seedの「生成後の制御」を固定してください。物語を書く欄は引き続き `request` 1つです。

## 検証範囲

単体テスト13件が成功しています。指定CLIPと編集したシステムプロンプトが `TextGenerate` に渡ること、JSON形式指定が残ること、旧APIの省略時に従来の指示が維持されること、GemmaとMOSSの配線が独立していることを確認しました。

### GPU0・RTX 4070での実機結果

- Gemma4 E4B INT8で台本→MOSS→H3動画保存まで成功：196.41秒。台本用CLIPは独立した読込ノード、MOSS用CLIPは従来のQwenを使用しました。
- 同じ台本用読込ノードのモデル選択だけをQwenへ戻し、台本生成に成功：18.33秒。こちらは動画の再生成を含みません。
- 両方のシステムプロンプトへ「各カットのカメラを固定カメラとする」方針を追加し、出力JSONの4カット全てで反映を確認しました。これは台本への反映確認で、映像のカメラが完全に固定されることを保証するものではありません。
- Gemma版動画は1024×1792、24fps、14.375秒。映像345フレームと音声450フレームを最後までデコードできました。
- 生成中はWebSocketで完了・エラー通知を待ち、通知後に履歴を取得しています。生成進捗のポーリングはしていません。

モデルは `Comfy-Org/gemma-4` の `gemma4_e4b_it_int8_convrot.safetensors`、8,090,965,702バイト、SHA-256 `974d0c838ef4ac1a989b06ccb4e57691c21b6270dd8e345ffa7531f9388f117c`。配布元のLFSハッシュとの一致を確認しました。

Gemma版の196.41秒と既存Qwen版の過去の計測値は、厳密な速度比較ではありません。モデルのキャッシュ状態や生成する台本・画像の内容が異なるため、読み込みコストや速度の優劣は切り分けていません。

## GUI読込時の設定値ずれへの対応

API形式で生成できても、GUI読込時にMOSSノードの保存値が位置順にずれ、`panels=496` や `panel_edge=8` などへ誤って復元される問題がありました。従来の検証は画面表示とAPI実行に分かれており、GUIが送信する値の検証が不足していました。

付属フロントエンド拡張で、`widgets_values_named` が保存されているノードの値を、GUI読込後に項目名で復元します。復元元の情報がない通常のワークフローは変更しません。値の修正はComfyUIの画面設定に対するもので、生成画像・動画の後処理は行いません。

更新時はComfyUIを再起動したうえでブラウザーを再読み込みし、repoの元のGUI用JSONを読み直してください。既にずれた状態で保存したファイルには復元元の情報がない場合があります。必要な依頼文やシステムプロンプトは読み直す前に控えてください。

master環境のGUIで読込み→APIエクスポートを行い、サンプルAPIの全入力との照合で差分がないことを確認しました。`widgetInputs.js` の非推奨警告自体を、この入力値の検証エラーの原因とは扱っていません。

修正後はmasterのGUI実行ボタンからGemma版を実行し、MOSS画像とH3動画の両方の保存に成功しました。実行時間は200.25秒。完了後の履歴でGUI送信値がサンプルAPIと一致することを確認し、1024×1792・24fps・14.375秒の映像345フレームと音声450フレームを全てデコードしました。システムプロンプトには固定カメラの方針だけを追加しています。旧版での画面表示確認と、今回のGUIからの実行確認は区別しています。
